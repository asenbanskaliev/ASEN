# ECO-06 — orchestration runtime audit

## Decision

**PARTIAL / OPEN.** ASEN can turn verified ODD facts into a persisted executable Todo DAG, continue dependency-ready `primary` work in the active Pi session, dispatch read-only roles including clarification, and run a bounded `worker` through a candidate-bound, explicitly authorized lifecycle. The worker is persisted as a descriptive record before dispatch; write authority remains in memory and is never restored after restart. A linked task remains blocked for independent review after the agent returns. Structured apply-phase grants are now bound to task, session, project, candidate, exact write surfaces, and the `read/edit/write` Pi tool set. ECO-06 remains open pending a real Pi interruption during a partial write, followed by safe inspection and a newly planned, freshly authorized writer run.

The current follow-up connects the active global Pi profile to production `/asen-plan` role routing and persists each selected model/thinking choice with its planned task. The child runner now accepts an explicit `ASEN_AGENT_PROVIDER_CREDENTIAL` selector from the existing provider allowlist, enabling NVIDIA credentials for selected child Pi agents while keeping the default credential-free and excluding the selector from child environments. Focused tests verify worker/reviewer/verifier routing, persistence without secrets, and dispatch through the production extension. This wiring enables a real NVIDIA worker test; it is not itself evidence of an interrupted writer recovery, so the closure gate above remains open until the exact Pi E2E and independent review are evidenced.

## Implemented and exercised

- The model-facing `asen_plan_request` bridge accepts ordinary-language requests through the Pi coordinator, which is instructed to derive ODD facts from read-only project inspection; it creates task identity internally, then reuses the existing ODD route, skill selection, DAG materialization and atomic session/project Todo persistence. The lower-level `/asen-plan` materializer still accepts validated ODD facts for internal use.
- Changing the Pi session or project while planning or dispatch confirmation is pending rejects the operation. Read-only dispatch revalidates identity after confirmation and repeatedly inside the Todo launch lock, including immediately before the trusted binder starts the agent.
- `asen_plan_dispatch_next` selects one dependency-ready task by saved priority, verifies current session/project identity and skill selection, then continues primary work or starts read-only roles without a second confirmation. Material clarification pauses for the user; a controlled writer still requires fresh explicit authorization bound to its candidate and exact scope.
- A `clarifier` is durably queued with its exact role provenance and no candidate, write surfaces, phase grant, writer admission, or delegated skill phase. Identity/revision drift, decline, and oversized instructions launch nothing and leave the Todo planned. Under the existing Todo launch lock, the complete confirmed snapshot is matched before enqueue, so concurrent dispatch admits one durable agent and instruction, plan, or dependency drift admits none. Its link remains persisted before runner start, and successful output leaves the Todo blocked for explicit acceptance.
- A planned worker retains the exact original ODD authorization facts, candidate revision, and ordered write surfaces. Before asking permission, dispatch recomputes ODD routing, checks the candidate is current, verifies the selected skills and surfaces, and requires an organic bounded lifecycle. After the visible Pi confirmation, it rechecks project/session identity, the persisted Todo revision and plan, and Git HEAD. It then creates one-use writer admission and binds the Todo/agent link before running the worker.
- Only organic bounded worker changes are supported by this path. The Pi confirmation displays the candidate and exact write surfaces and instructs the worker to stop without committing or merging. The runner receives a one-use bound receiver; it does not receive the admission token itself.
- `PersistentAgentStore.enqueueControlledWorker` persists only the worker's descriptive task record. Candidate, write surfaces, skill context, and writer admission are omitted from the durable agent record, so restarting cannot replay the write. An interrupted worker requires a fresh plan and explicit authorization.
- Worker success is reconciled to `blocked`, not `done`. `asen_todo_accept_result` displays the saved terminal result and requires independent confirmation that the actual diff stayed within the approved surfaces and met the acceptance criteria.
- `TrustedTaskAgentBinder` persists Todo ownership and the agent link before the Pi runner starts. Agent terminal outcomes reconcile to `blocked`; they never complete a Todo.
- `asen_todo_accept_result` requires a blocked planned task, an immutable task-agent link, matching session/project/role, a durable successful terminal agent record, a bounded full result view, independent user evidence, and explicit Pi UI confirmation. Direct `done` is rejected for a linked plan task. Acceptance is persisted as ordered `running` then `done` events, so a crash between them recovers to review rather than completing silently.
- Interrupted linked read-only work requires explicit continuation; failed linked read-only work permits one explicitly confirmed retry. Both bind the child attempt before dispatch. Writes and cancelled tasks are not retried.
- The primary role runs in the active Pi turn, without creating an agent or receiving a write grant; a compare-and-swap Todo claim prevents duplicate advancement.
- `asen_todo_inspect_interrupted_write` is a read-only recovery aid for one interrupted writer linked to the exact active session and project. It compares the saved candidate revision with current Git HEAD, reports tracked/untracked paths and additions/deletions against the approved scope, and never returns file contents or changes the worktree. It requires a new plan and a new explicit authorization before any later write.

## Remaining work

- Structured phase grants are issued only after explicit worker confirmation and are wired through the persisted Todo launch boundary into the live dispatcher. The opaque grant is never stored; interruption or restart requires actual-state inspection and a new plan and authorization before writing.
- The agent record intentionally does not preserve write authority. A process restart cannot resume a partially executed writer automatically. The new inspection test is local deterministic Git evidence, not an abrupt Pi SIGKILL recovery receipt; ECO-06 still needs the full Pi-host interrupted-write and fresh-authorization journey.
- Plain text passed directly to the lower-level `/asen-plan` command still produces conservative missing-fact triage. The chat bridge relies on the configured Pi model to follow coordinator guidance and infer facts; this deterministic local change does not prove behavior with a live provider.
- Acceptance is an explicit human review of the persisted result and recorded acceptance instruction; ASEN does not execute arbitrary acceptance commands inferred from agent output.
- Concurrency is bounded by the agent dispatcher and each advancement starts one dependency-ready task. Read-only progression has no extra user dialog; writers remain one-at-a-time and explicitly authorized. There is no automatic multi-writer scheduler or provider quota policy.

No permission is inferred from a plan, model response, skill selection, or successful agent completion.

## Authorization snapshot race correction (2026-10-14)

Independent review found a gap between the worker's post-confirmation snapshot check and `TrustedTaskAgentBinder.launch`: a concurrent Todo transition could occur before the binder acquired the launch lock. The old worker path accepted an already-running Todo and could therefore dispatch work authorized against a stale snapshot.

The controlled worker now receives enqueue and dispatch callbacks only through `launchExact`. The binder compares the complete persisted Todo and requires `planned` while holding the same lock that records the running claim, binds ownership, and dispatches. The agent record is not durably enqueued until that exact comparison succeeds. The worker path has no direct-dispatch fallback. `tests/trusted-task-agent-binder.test.ts` reproduces the stale-state race and requires zero enqueue, zero link and zero runner calls; `tests/pi-agent-runtime.test.ts` continues to cover the approved writer path.

This closes the local stale-snapshot admission gap only. ECO-06 remains **PARTIAL / OPEN**: real interrupted-write recovery and native review remain separate gates.

## Structured plan-writer phase grant tranche (2026-10-15)

The controlled plan writer now receives an opaque, one-use `apply` grant after the exact Todo snapshot passes the launch lock and the user confirms the candidate and file scope. The private grant binds task ID, session, repository, candidate ID/revision, ordered write surfaces, and the allowed Pi tools (`read`, `edit`, `write`). The dispatcher and Pi runner both require and consume that grant; an omitted, replayed, mismatched, or out-of-scope grant fails closed. The write-capable Pi invocation has no shell, commit, publish, or merge tools. The grant is removed before the descriptive worker record is persisted and cannot be restored after restart.

Evidence added in `tests/dispatcher.test.ts` and `tests/pi-agent-runtime.test.ts` covers exact phase/scope/session binding, a single concurrent winner, missing and forged grants, persistence stripping, and independent result review. Focused validation passed 72/72 across dispatcher, lifecycle, Pi runtime, and interrupted-writer persistence suites. This closes the local phase-grant wiring gap; it does **not** prove a live Pi process was killed during a partial file write and safely reauthorized afterward. ECO-06 remains **PARTIAL / OPEN** pending that exact Pi-host experiment and independent native review.

## Real Pi writer E2E gate (2026-10-16)

Added `.github/workflows/eco06-nvidia-e2e.yml` and `scripts/eco06-pi-writer-e2e.mjs`. The workflow is restricted to the PR branch and pins the event SHA before installing the real Pi 1.1.0 runtime. It checks `NVIDIA_API_KEY` only for presence, never prints its value, and uploads a SHA-named artifact even when the preflight is blocked.

The harness creates a disposable Git candidate with one permitted file. ASEN builds a real worker plan and asks for a one-run write authorization; `PiProcessRunner` starts Pi 1.1.0 with the NVIDIA Nemotron route and only the selected NVIDIA credential. Once the file changes, the controller kills the ASEN host with SIGKILL. A second host reopens the same persisted stores, verifies there was no automatic provider invocation, and invokes the read-only interrupted-write inspection. The harness compares file digests before and after inspection. It then preserves the reviewed partial bytes as a clean checkpoint in the disposable candidate (Git metadata changes; the file bytes do not), and requires a new plan and a second explicit write authorization. It finally dispatches a separate read-only reviewer and checks exact marker counts, worker/reviewer identities, persisted states, and that review did not modify the worktree.

Local evidence for the harness is limited to syntax checks, typecheck/build, the focused ECO-06/dispatcher/Pi integration suites, and a smoke test that starts the ASEN host and confirms it creates one writer plan. The NVIDIA provider journey has not been run locally. The full local suite reported 1,503 passing, 13 skipped, and one process-tree observation failure in `tests/pi-process-runner.test.ts`; the recorded descendant PID resolved to the Codex execution host (`tokio-rt-worker`). No production process-runner change was made based on that environment-specific observation.

**ECO-06 remains PARTIAL / OPEN.** It can be reevaluated only after the new workflow succeeds on its exact published SHA and the artifact proves every interruption, recovery, inspection, renewed authorization, second write, independent review, and no-duplicate assertion. A missing secret, provider failure, incomplete artifact, or failed check is not a PASS and must not be used to mark ECO-06 FULL.

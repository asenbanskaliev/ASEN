## A4R finding: malformed checkpoint phase

### Evidence → reproduction

At baseline, `restoreCheckpoint()` checked checkpoint version, project identity, candidate identity, skill context, and agent lifecycle. It trusted the deserialized task phase through a TypeScript assertion. The persisted value is untrusted runtime data; compile-time types do not validate JSON.

The test-only commit `96314441ae67f9331f62f18b5a04c01c2beaf727` added a 12-line deterministic adversarial test. It serializes and parses a valid checkpoint, changes its task phase to `ROOT`, then requires recovery to throw.

- CI run `37692689110`, Ubuntu job `113036542611`: failed at the new assertion with “Missing expected exception”; 984 passed, 1 failed of 985.
- Release Gate run `37692689173`, Ubuntu package job `113036542964`: failed on the same assertion.
- These are two workflows observing one defect, not two defects.
- CI Windows/macOS were cancelled after Ubuntu failed.
- Phase 0 run `37692689181`: success.
- Pi Free run `37692689149`: skipped.

### Cause → existing mechanism → decision

Cause: runtime checkpoint restoration did not validate an externally persisted discriminant, despite `TaskState.phase` being a closed union.

Related mechanisms: `loadCheckpoint()` routes deserialized state through `restoreCheckpoint()`; session recovery already binds project/session/repository/revision and treats checkpoints as recovery hints. The missing check belonged at this existing boundary.

Decision: BUG, reproduced. No second checkpoint system, store, authority, or coordinator was needed.

### Minimum repair → proof

Commit `ccfd8e42f2225ce168f334ae02aa9f010f59929a` added validation for the closed set of task phases on checkpoint create and restore. Commit `764c0f6282522b723274fb5cb11cba9eb1b7bb93` represented that set as an exhaustive `Record<TaskState["phase"], true>`, so adding a phase without updating the runtime allowlist is a type error.

The diff from baseline to `764c0f6` was 2 files, 16 additions, 0 deletions: 12 test lines and 4 production lines. The test is deterministic and requires fail-closed recovery. Existing real session restart/recovery tests remain in the full suite. This new probe itself calls the restore boundary with JSON-round-tripped data; a dedicated corrupt-on-disk restart test was not added.

## Adversarial and related test coverage

The experiment’s new probe invalidated checkpoint state and reproduced the missing guard. The existing baseline suite also exercises authority falsification/reuse, candidate and identity mismatches, stale lifecycle timestamps, process/runner failure, project/session isolation, lock concurrency, malformed stores, replay, and real session restart.

The probe directly tests JSON-roundtripped invalid state passed to `restoreCheckpoint()`; it does not separately kill a process between save and restore while the checkpoint is corrupt. Existing restart E2E covers valid recovery, not that exact adversarial combination. Timeout/cancellation/provider failure were not independently invoked for this deterministic defect because they do not affect the checkpoint phase invariant.

## A4R self-audit

- Audit/reduce were useful because they pointed to the existing restore boundary and prevented a parallel persistence architecture.
- The full release/CI matrix was expensive relative to a four-line runtime correction. Running both workflows concurrently duplicated broad test work; the accidental duplicate same-SHA runs added cost without new evidence.
- Revalidation remains justified for recovery code, but future study should specify proportional CI intensity by change risk and avoid opening/reopening a PR merely to trigger already available checks.
- No provider/model was needed. Adding one would not improve evidence for a deterministic persisted-data invariant.
- A4R did not force a production feature; reduction correctly limited the change to a validation guard.
- Five phases were useful in this high-risk recovery example but this one case does not establish that all five are useful for routine changes.

## Decision

**REVISE.**

Evidence demonstrates that the audit + adversarial probe found one real checkpoint recovery defect and that a minimal fail-closed correction passed the targeted test and the Ubuntu Release Gate. The experiment also found and repaired one documentation artifact that failed the repository’s upstream boundary audit. Evidence does not yet demonstrate consistent benefit over the baseline process: one product defect is a small sample, the A/B comparison is historical and unmatched, and two unrelated CI tests failed once each before passing same-SHA retries. The methodology also incurred redundant same-SHA workflow executions.

A follow-up should compare matched, independently reviewed tasks across risk categories, measure total engineer/CI cost, and define a proportional validation gate before considering broader adoption. Do not implement A4R in ASEN. Adoption as an ASEN user-facing capability is a separate decision and was not tested.

## A4R self-audit and proportionality

The evidence supports conditional intensity, not five heavyweight mandatory phases for every task:

- **Audit:** retain a short contract, ownership and source-of-truth check for nontrivial work; go deeper for authority, recovery and durable state.
- **Reduce:** make an explicit reuse/composition decision; do not require code deletion or an optimization.
- **Break:** probe only material invariants. The checkpoint probe was valuable because persisted JSON crossed a typed boundary.
- **Repair:** keep the reproduced-defect gate and minimum-fix rule.
- **Revalidate:** focused tests first; existing platform/release matrix when code touches recovery, authority, persistence, concurrency or release behavior. Avoid broad reruns for documentation-only edits or without new evidence.

This is a proposal for another evaluation, not a new product mode. The sample does not demonstrate that risk-scoped A4R outperforms ordinary careful development.

## Final decision after phase two

**REVISE.** A4R demonstrated one useful recovery defect discovery and a minimum fix validated cross-platform. It did not produce an independent matched eight-case trial, per-case cost data, or a second product defect to establish consistency. Risk-scoped benefit remains plausible but unproven; do not adopt or productize A4R in ASEN. No R01–R20 state changes are justified.

# ASEN runtime tools and registry lifecycle

These interfaces are registered by the shipped primary extension (`asen/extensions`). They are bounded implementations, not complete ecosystem parity. The current claim registry remains authoritative; local fixtures do not establish all-platform host behavior.

## User interaction

`asen_ask_choice` accepts a question, optional header, and two to four options. Each option has a label, optional description/preview and a unique value. `ask_user_choice` is the canonical compatibility alias: it uses the same strict input checks, excludes `preview`, and reports the selection index starting at one. The ASEN-named tool keeps its existing zero-based index.

`asen_ask_question` accepts one to four questions. Each has a question, header and two to four labeled options; `multiSelect` is optional. `ask_user_question` is registered as a compatibility name and currently uses this ASEN input and result shape; exact canonical result translation is still pending. A cancelled questionnaire discards all partial answers. Custom free text, where explicitly enabled by the choice contract, is validated and remains data. Neither tool issues permissions or a write grant.

The native Pi select/input primitives carry interaction. Offline Linux RPC choice/cancellation has been tested with zero model turns. Full TUI/questionnaire presentation and integration with genuine human-only mutation consumers remain open. Timed-out hosts that ignore abort stay quarantined until the old dialog settles.

## Independent code review

`/asen-review workspace` captures current tracked/index changes plus explicitly selected untracked files as a Git tree, without moving HEAD or modifying the contributor index. The user specifies the exact paths included in the review, including deleted files, and separately specifies untracked files to include. The command blocks changed paths outside the selected review scope and unexpected untracked files before storing changed Git objects, creating the view or calling the reviewer. Projection still reads tracked paths to determine which ones changed, and an admitted view materializes the complete candidate tree, including unchanged files outside the review selection. This selection restricts the review; it does not grant or verify write permission or isolate the workspace. The command derives the complete diff, changed paths, tree identities and candidate file bytes from the captured tree. Detected source, index or view drift invalidates the session and result. The view permissions and path checks do not isolate it from a hostile process running as the same user.

The user selects an authenticated Pi model distinct from the current author model, enters review requirements, and explicitly confirms sending the exact candidate evidence to that provider. The reviewer receives a fresh tool-free Pi model call with the requirements, full diff, changed file contents, source identities, risk lenses, and test status. Output is schema-checked and bound to that exact candidate. Provider/model identity is descriptive evidence of the configured call, not a human identity or delivery authority.

A failed review can issue one correction request. `/asen-review workspace correction <correction-id>` retains the original review scope and requires a different reviewer model and a changed candidate whose correction delta touches only files named by the findings. The captured delta is compared to a private prior-candidate catalog before changed objects or a review view are created; the constraint is retained on revalidation. This comparison is not an authorization to make the correction. A second failure blocks. A passing review remains `passed-awaiting-tests`; ASEN reports tests as `not-run` and does not accept or authorize delivery. Headless hosts, missing author identity, unavailable reviewer credentials, oversized evidence, cancellation or provider errors fail closed without a pass.

The correction map and review-view ownership claims are in-memory and session-bound. Restart requires a new review and does not recover an old approval. A model-backed review is evidence for the shown tree; it does not establish native RDD provider authentication, persistent result recovery, test execution, final acceptance or OS-level isolation. These remain T05 closure gates.

## Code intelligence

Pi exposes one CodeGraph tool: `codegraph`. It accepts `operation` (`init`, `query` or `explore`), an optional integer `limit` from 1 to 20 (default 10), and a nonempty query of at most 2,000 characters for query/explore. Read-only query/explore calls run without an ASEN confirmation and never initialize or retry automatically. `init` may create `.codegraph` only after a one-run approval in Pi's interactive UI; headless execution, denial, or cancellation performs no initialization. A successful index initialization is not repeated in the same Pi process, and an existing safe index is left alone.

The `asen_code_intelligence` adapter remains available to existing internal callers during migration, but is no longer registered with Pi or shown to the agent. It accepts only `query` or `explore`, requires the query, preserves its existing bounded statuses, and cannot initialize an index. CodeGraph requires the current working directory to be the canonical Git project root. Home/temp roots and nested working directories are rejected. Existing `.codegraph` entries are checked with `lstat`; symbolic links and non-directories are rejected without reading index contents.

Both names share hardened execution. The host resolves an installed CodeGraph executable; on Windows, npm package metadata resolves a contained JavaScript entry through Node rather than executing cmd/PowerShell shims. Processes use separate arguments, a constrained environment, no shell, bounded duration and bounded output. Queries follow `--`, so they remain one literal argument. Canonical output is truncated with an explicit marker; canonical failures include operation, workspace and fallback metadata. Compatibility failures remain sanitized and do not expose subprocess error output.

Tests use injected subprocesses and disposable Git fixture projects, including spaces/Unicode paths, hostile queries and unsafe synthetic index entries. No canonical `init` is invoked against an ambient workspace. Real CLI/version compatibility, initialization against a disposable real-CLI project, and cross-platform host behavior remain open. The installed CLI is trusted local code; this is not OS confinement. Existing authority gates still determine whether a tool may execute.

## Skill registry lifecycle

Startup refresh reuses `.asen/skill-registry.md`, its existing cache and optional memory mirror. Source precedence remains project, user, then package scope. Discovery does not alter mandatory behavior-Skill selection.
Repeated activation through the same loaded module and Pi host registers only one startup hook; separate copies loaded through different module paths still require real-host validation.

Interactive hosts watch existing source roots recursively, debounce changes and serialize writes per canonical project. Changes during refresh coalesce into a follow-up refresh. Project switching/shutdown invalidates old callbacks; shutdown closes watchers, cancels scheduled refresh and waits for in-flight work. Unsupported watchers produce a diagnostic and leave manual refresh available. Missing or recreated source roots may require manual refresh or restart.

Disable automatic startup/watch with either of:

- environment variable `ASEN_NO_SKILL_REGISTRY=1` (`true`, `yes` and `on` also apply);
- Pi `--no-skills` or `-ns`.

ASEN does not register a separate CLI flag because Pi's public extension API has no complete flag inventory for collision checks.

`/asen-skill-registry refresh` remains an explicit manual command. Startup/watch failure is diagnostic; it does not cancel the user's final response. Local native Linux watch invalidation, restart generation, shutdown, disable and project isolation are tested. Real all-platform Pi startup/restart journeys remain open.

## Local usage and observed history statistics

`/asen-usage` reports ASEN's local session, command and turn counters, not model tokens or billing. Telemetry preview and consent remain local-only; no telemetry transport is configured. These operational counters are separate from Pi history measurements.

`/asen-stats [from=YYYY-MM-DD] [to=YYYY-MM-DD]` freshly scans the active Pi session directory, restricted to the current canonical project and existing bounds. Its command JSON uses `asen.pi-history-stats/v2`: `inputTokens`, `outputTokens`, `totalTokens` and `costUsd` are `null` when that exact field was not observed. A valid recorded zero remains `0`; partial records do not imply totals, prices or cost. `measurementCounts` gives the number of valid observations for each field. Non-null values are observed subtotals and may be incomplete when history or individual measurements are missing, rejected or truncated. `state: "available"` describes history access, not complete measurement coverage.

The source-level collector retains `asen.pi-history-stats/v1` and its numeric totals for compatibility, adding observation counts. Consumers of `/asen-stats` JSON must accept the explicit v2 schema and nullable measurement fields rather than treating missing history as zero. Range validation, privacy, corruption handling and numeric saturation remain unchanged; collection writes no history data.

History-reported cost is not verified provider billing. Neither command proves provider-used routing or enforces provider request/token/spending limits; ASEN does not invent prices, quotas, or measurements from profile choices.

## Runtime profiles and routing visibility

`/asen-profiles` preserves its existing `active`, `profiles` and `available` fields and also reports the active global profile's effective role choices. These values are configuration: `requested` and `resolved` describe ASEN's selected model/thinking values, `source` identifies the global profile or persisted plan, and `actual` remains `unknown`. A queued request or emitted child flag does not prove which model or effort a provider actually used.

At session startup, ASEN copies the active global profile for that exact session and canonical project. A direct unbound `asen_agent_start` and newly materialized plans use this frozen inherited profile; if routing precedes startup, the first route captures it instead. A consented foreign project receives a separate snapshot. Later global changes affect only new captures. Missing configuration freezes provider defaults; malformed or unreadable configuration fails capture rather than saving a false default. Duplicate startup and extension reload preserve the first snapshot. Shutdown clears only that session's snapshots within the same configuration partition and invalidates pending reads.

`/asen-profiles` keeps its global inventory fields and, with a live session context, adds `sessionProfile` with its exact identity, chosen profile, inherited or `explicit-session` source and role choices. The global inventory can therefore differ from the session's frozen selection. Calling the inventory without a session context retains its previous output. These snapshots contain routing data only, never permissions, approval, credentials or provider availability; `actual` stays `unknown`.

Profile commands:

- `/asen-profiles` or `/asen-profiles show`: show current global inventory and this session's effective snapshot.
- `/asen-profiles session <profile>`: copy an existing named profile for this exact live session/project, without writing global settings. Selection replaces the whole profile, not individual missing roles or fields. Later edits to its saved definition do not change this copy.
- `/asen-profiles session --inherit`: remove the explicit choice and reveal the original inherited snapshot, not today's global value. A saved profile named `default` remains selectable with `session default`.
- `/asen-profiles global <profile>`: atomically select the global active profile using the existing validated store. Only future captures see the change; bound inherited or explicit sessions keep their snapshots.

Invalid syntax reports `Usage: /asen-profiles [show | session <profile> | session --inherit | global <profile>]`. Unknown names or invalid/unreadable configuration fail without applying a selection. Pending selection is invalidated by shutdown, reset or a newer selection intent; failed newer input preserves the previously committed choice. Session selection requires a valid live session/project, and does not grant access to another project.

A Todo with persisted plan metadata uses that complete saved route instead, including omitted model or thinking fields as provider defaults; profile changes cannot fill those omissions. Legacy Todos without plan metadata use the session's effective explorer route at their initial launch. No model/thinking tool parameters, project pins, provider discovery, pricing data or observed-child state are added here.

A confirmed failed read-only retry preserves the failed attempt's saved model and thinking, including omitted provider defaults, for planned and legacy Todos. Later profile selection never replaces or fills that saved route. Continuation likewise preserves the interrupted request's saved route. Existing retry confirmation, ownership, instruction and single-attempt restrictions remain unchanged.

### Optional child-selection observations

`PiProcessRunner.subscribeChildSelection(listener)` is an opt-in, nonpersistent runner API. A launch captures the current subscription tokens and its task/session/canonical-project identity. With observers, successful policy/skill preflight sends one separately correlated `get_state` request before the prompt, without waiting for state. With no observers, the previous prompt protocol is unchanged.

An observation is labelled `source: "child-reported"`: it contains only the frozen identity, bounded control-free model provider/id (or explicit `null`) and an optional supported thinking value. It does **not** prove provider-used model, reasoning behavior, tokens, billing or limits. Unsupported, malformed, duplicate, mismatched and late state is ignored; raw state is excluded from retained execution output. Unsubscribing invalidates launch-captured delivery, even when the same callback is added again. Observer exceptions do not alter task execution.

Observations are not added to `AgentResult`, persisted records, receipts, `/asen_agent_status` or routing `actual` fields. They do not provide durable status visibility.

When the extension owns the composed runner and that runner supports observations, the active session can receive `ASEN child-reported selection (<task-id>): model <provider>/<model>; thinking <level>.` A reported null model or absent thinking is shown as `unavailable`, never as inferred provider use, zero usage or zero cost. The notice requires an existing task owned by the exact current session and canonical project; context ownership is rechecked after asynchronous queries. Startup/replacement rotates the subscription before waiting, and shutdown invalidates its owned subscription before cleanup. Old launches and in-flight notices cannot transfer to a replacement context; an unrelated old-session shutdown does not disable the new selection owner.

A runtime supplied through `agentRuntimeFactory` does not expose its actual runner, and an ordinary runner may not implement observations. These paths preserve execution without selection notices; an unrelated injected runner, requested flags or profile choices are never substituted as observed evidence. Unsupported child state likewise produces no notice. All presentation remains ephemeral and grants no permission or task acceptance.

## Persona style

`/asen-persona` reports the effective communication style. `/asen-persona professional` and `/asen-persona neutral` select one of the two package-owned styles; arbitrary persona text is rejected. With no saved configuration, `professional` is the default.

Selections are stored atomically in `~/.asen/persona.json`. If the active project already has `.asen/persona.json`, the same selection updates that existing override as well. ASEN never creates a project override automatically. An existing project value takes precedence when the effective style is read. Malformed or unsafe state is reported as unavailable rather than as a successful write.

The effective text is added only to the `asen_persona_style` prompt section. Persona selection does not change runtime profiles, model or thinking choices, tools, permissions, confirmations, task state, acceptance, or writer admission.

## Project memory

The primary Pi extension opens the private local SQLite store at `~/.asen/memory.db` when memory is enabled. At session start it binds a fresh memory session to the canonical current project and Pi session. Before each agent turn it adds only bounded project context: recent/pinned notes on the first turn and project-search matches for later requests, capped at 4 KiB. A project/session mismatch or unsafe store prevents memory access and never broadens retrieval to another project.

`asen_memory_save` stores curated project decisions, conventions and non-obvious discoveries. `asen_memory_search` retrieves bounded matches. The injected policy tells the agent to avoid transcripts, routine actions, credentials, personal data and temporary task checklists. On session shutdown ASEN stores a short summary of notes saved during that session; the next session can read it. A crash may skip the summary, but saved notes remain durable. Memory remains reference data and never restores write permission or resumes a task.

`/asen-memory status`, `/asen-memory search <text>` and `/asen-memory forget <id>` let the user inspect or remove local notes. Forget requires a live Pi UI confirmation and removes the affected session summary so deleted content is not reintroduced through that summary. Search and context remain project-scoped.

A project memory export reads observations, relations, summaries, sessions and deletion markers from one consistent project snapshot, while WAL writers may continue committing. The export is not a backup of all stores, personal configuration or provider state, and importing it does not restore task or execution authority.

The internal `createProjectMemoryBackup` API publishes one explicitly selected project's validated export to an explicit absolute destination. The destination's parent must already exist as an ordinary, non-linked directory. The API does not choose a project or path, create directories, expose a CLI command, discover other files, restore data, or grant import, execution, consent, or maintenance authority. Existing destinations are preserved and refused; publication fails closed when the parent, temporary file, destination, or hard-link result cannot be safely revalidated.

A backup is bounded to 16 MiB for the complete UTF-8 JSON envelope. It is plaintext and can contain sensitive text already present in project memory; it is not encrypted or automatically redacted. Its domain-separated SHA-256 integrity fields detect byte changes but do not authenticate the author or establish trust. Session status in the payload is descriptive historical data, not live runtime permission.

Publication uses one same-directory create-new temporary file and one hard-link operation, followed by physical-identity and full-byte readback. It never overwrites or deletes the destination and has no rename or copy fallback. A confirmed readback does not prove directory-entry persistence across sudden power loss. If publication or cleanup becomes uncertain, the result reports `unknown` or a retained temporary path rather than deleting the destination as compensation. Unsupported filesystems fail closed. Actual restore and safe store reopening remain a separate lifecycle unit.

Legacy memory import remains permissive about unknown DTO fields and retains its existing relational validation behavior. The backup boundary is intentionally stricter: it accepts only the known version-1 project export fields with explicit sessions and valid project, ancestry, relation, summary, and deletion references.

These deterministic lifecycle tests use a local SQLite file and simulated Pi events; they do not establish a provider-backed Pi conversation or cross-platform host evidence.

## Primary installation and child policy

The shipped primary extension installs one pre-execution `tool_call` guard. For Pi's built-in `read`, `edit`, `write`, `grep`, `find` and `ls` tools, path inputs that contain a `.git` component, a component beginning with `.env`, or a component ending in `.pem` or `.key` are blocked. No broader secret-name list is implied. Checks use both the normalized lexical path and the symlink-resolved path; a missing target is resolved through its nearest existing parent so a symlinked parent cannot hide a protected name. Malformed or ambiguously unresolvable path inputs fail closed.

Directory calls are also checked for protected descendants before execution. `ls` checks every direct entry because those names would be returned. ASEN scans the recursive search tree used by `grep` and `find`, including `.git`, follows directory symlinks for the safety check, detects cycles, and allows a clean tree only within 10,000 entries and 64 levels. Exceeding those bounds or encountering a protected, unreadable or unresolvable subtree blocks rather than risking disclosure. This preserves ordinary file access and bounded clean-directory use, but a parent traversal containing any protected descendant is intentionally unavailable.

Primary shell admission follows Reference Shell 4.3.0 Normal-mode selection for the exact tool names `bash`, `bash_background` and `monitor`; ASEN does not register the latter two tools. It classifies the raw model `command`, not Pi's configured shell prefix or another effective-command expansion. Ordinary and malformed/non-string shell inputs pass through without a dialog, including in headless hosts. Recognized hard destructive forms (for example `git reset --hard` or `rm -rf /`) block without a dialog. Guarded forms such as `git push`, `npm publish` and recognized non-hard filesystem/database data loss require a fresh confirmation for every call. Within the already declared forced-branch-deletion deny class, ASEN additionally recognizes Git global options (`-C`, `-c`, `--git-dir`, `--work-tree`, including value-attached forms), wrappers/absolute Git executables and separated force/delete flags. Installed Reference Shell 4.3.0's direct branch pattern misses those global-option variants, so this targeted S4 hardening is an explicit difference rather than byte-for-byte parity. The dialog title is ASEN-owned and its body is the classifier's whitespace-collapsed, trigger-adjacent raw-command preview, capped at 180 characters; it is intentionally not a full command/cwd display. Missing UI, decline or cancellation blocks. A rejected confirmation promise is allowed to propagate so Pi's actual pre-execution host pipeline fails closed rather than executing the tool.

`powershell` and `pwsh` are not recognized shell names in this Normal-mode classifier, so this guard passes them through unclassified; that is not a claim that they are safe. ASEN does not add PowerShell, background-shell or monitor tool registration. There are no cached/session grants, and descriptions, memory or prior approval cannot supply permission. This selective policy does not adopt Reference Shell YOLO/Auto modes, lifecycle events, permission stores or unrelated providers.

This guard is an extension hook and lexical admission layer, not a shell sandbox or OS confinement boundary. A pass or approval does not make a command safe. It does not intercept `user_bash`, another extension's direct `pi.exec`, unknown custom-tool internals, or a hostile extension outside/after the hook. A passed or approved shell can also read sensitive files outside the file-tool checks; the `.git`/`.env*`/`*.pem`/`*.key` protections apply to the named file tools, not arbitrary shell behavior. Filesystem changes between path checking and tool execution remain a TOCTOU residual, so this policy does not claim filesystem confinement. Provider-free `AgentSession`/extension-runner/agent-core checks prove the production hook vetoes a sensitive built-in write before its file executor changes the target on the specifically tested Pi host; the version gate alone is not compatibility proof for every future Pi release.

The Pi package manifest selects `extensions/asen.ts` explicitly. `extensions/authority.ts` is a private, hash-pinned policy loaded explicitly by the existing child runner; ordinary installation does not replace or weaken that child authority with the primary policy. `verify:pack` installs the actual tarball with the optional peer omitted, asserts that the peer is absent, then loads the tarball through the real Pi SDK resource loader and rejects accidental child-policy activation. This offline registration check does not execute tools or models, and does not prove complete ecosystem integration.

ASEN child Pi agents receive no provider credential by default. To route controlled agents through NVIDIA NIM, configure the Pi profile at `~/.asen/profiles.json` with an active profile that defines the required role routes, for example `{"schema":"asen.runtime-profiles/v1","active":"nvidia","profiles":[{"name":"nvidia","routes":{"worker":{"model":"nvidia/nemotron-3.5-lightning-30b-a3b","thinking":"low"},"reviewer":{"model":"nvidia/nemotron-3.5-lightning-30b-a3b"},"verifier":{"model":"nvidia/nemotron-3.5-lightning-30b-a3b"}}}]}`. Set `NVIDIA_API_KEY` in the process environment and `ASEN_AGENT_PROVIDER_CREDENTIAL=NVIDIA_API_KEY`; ASEN then passes only that selected credential to child Pi processes. The selector accepts only the provider credential names in the Pi runner allowlist, never accepts credential values, and is not itself forwarded to children. Do not store API keys in the profile file. This config routes delegated agents; it does not change the model selected for the primary Pi session. If no selector is configured, child processes receive no NVIDIA credential and authenticated NVIDIA calls cannot run.

## Public Pi command boundary

The production factory requires a strict release version at or above Pi `1.2.0`, matching the optional peer range `>=1.2.0`; there is no upper version cap. Passing this version gate does not prove compatibility with every future host. The factory validates public registration APIs before adding a bootstrap session handler. Pi does not provide mode or initialized command/tool inventories to the factory, so ASEN follows the normal delayed-activation policy: at the first `session_start`, after Pi initializes those public inventories, ASEN validates the execution mode and complete command/tool snapshot before its first command or tool mutation. Missing, malformed or initially colliding inventories fail closed and may retry on a later session; a host error after partial registration leaves those handlers inert and requires a Pi reload. This preserves ASEN's initial collision preflight, not an arbitrary late-registration veto.

After that initial snapshot, foreign extensions that register duplicate names are governed by Pi's native precedence and disambiguation behavior. Pi exposes no public registration interception or complete flag inventory, so ASEN neither guarantees a late sibling veto nor registers a private CLI flag. Command, tool and event handlers still validate the public execution context mode (`tui`, `rpc`, `json` or `print`) before running. Historical packed-artifact checks on older Pi releases remain historical evidence only and do not satisfy the current minimum. Current-host and broader platform/mode coverage are recorded separately; Windows/macOS, clean exit across all four modes, and representative coverage beyond the tested host still need real-host validation.

The data commands publish through `ctx.ui.notify`; their production handlers fulfill Pi's `Promise<void>` contract. Internal `createAsenExtension` handlers retain their returned data for composition/tests. `/asen-route` remains an advanced read-only diagnostic for exact ODD facts; ordinary users can describe the task in chat. The Pi coordinator is instructed to inspect the active project read-only, derive ODD facts internally and call `asen_plan_request` for tracked or multi-step work. That tool creates the task identity, binds the repository to the active Pi project, and passes the derived facts through the same ODD decision, orchestrator, skill selection and executable DAG. With the Todo runtime enabled, the plan is persisted atomically as session/project-owned tasks and dependencies; planning does not retrieve information, request review, issue execution authorization, or dispatch agents. The lower-level `/asen-plan` command remains an internal materializer for callers that already have validated ODD facts; plain text there returns conservative missing-fact triage. `asen_plan_dispatch_next` continues one dependency-ready primary task in the active session or automatically dispatches one read-only role (`explorer`, `reviewer`, or `verifier`) after checking current skill selection and session/project identity. Material clarifications pause for the user. A writer still requires a fresh candidate and explicit authorization limited to its exact file scope; linked results remain blocked until independently accepted.

When a plan is active, `before_agent_start` adds a short role/status summary to the prompt for the exact current Pi session and project. It omits task IDs and task descriptions, is capped at 2 KiB, and is reference-only: it neither resumes blocked work nor grants permission. If the Todo store is unavailable or identity changes during retrieval, the turn continues without the summary.

`/asen-changes` is filtered to the current session, canonical project and worktree. It flags a potential conflict when successive successful change records for one relative path name different actors. Windows and macOS comparisons fold path case to catch common case-insensitive collisions; this can conservatively report distinct names on a case-sensitive macOS volume. The append-only store has no content snapshots, so this is a review signal only: it does not prove a lost update, select a winner, clear a conflict, or authorize a write. The command does not inspect another session's changes. Before truncation, change and conflict rows replace Unicode control/format characters (including ESC, BEL, C1 and bidirectional controls) and line/paragraph separators with visible `�` characters. This applies to displayed paths and actor/operation text, including injected change providers; stored attribution, path comparison and conflict detection remain unchanged. Ordinary Unicode is retained, and the existing string-length limits remain in effect; this is not a grapheme-aware terminal-column layout guarantee. Rendering neither rewrites the history nor grants authority. Authorized resolution and broader workspace actions are not implemented.

`/asen-history search <text>` returns a JSON array of at most 50 newest matching entries from the current project. Each result contains only `id`, `timestamp`, `redacted` and `preview`, rather than full history records or session/project identifiers. Previews reuse the selector's sanitization: terminal control-string payloads are discarded, control/format characters removed or collapsed as whitespace, and text is limited to 160 Unicode codepoints including an ellipsis when truncated. Query matching and credential redaction are unchanged; no matches return `[]`. Search neither changes stored bytes/revisions nor authorizes selection or deletion. Explicit `export` retains its existing full redacted-record format; consumers needing that format must request export instead of relying on search output.

`asen_todo_update` requires active Pi UI confirmation before resuming a blocked Todo. A planned task needs a verification summary and user confirmation before completion; if a Pi agent is linked, direct completion is rejected. Use `asen_todo_accept_result` to select the exact persisted linked agent result. It requires matching session, project and planned role, a successful terminal record, a complete result that fits the bounded review view, independent user evidence, and explicit Pi UI acceptance. Acceptance is written as `running` then `done`, so interruption between those events recovers to review. Agent completion alone never closes a Todo. Model-generated reviewer/verifier verdicts are treated as untrusted results, never as approval; neither they nor a passing-looking summary can complete the review task or its upstream writer without explicit user acceptance.

After a planned Todo is independently accepted as `done`, ASEN automatically checks for and starts the next dependency-ready task. Read-only steps continue automatically; a writer still receives the existing exact-scope Pi approval. If advancing fails, the accepted result remains saved and the user can simply ask ASEN to continue; internal task IDs and slash commands are not required.

Agent task delivery and project access: `asen_agent_status` accepts an optional `id` to return that owned task's durable state and history without its prompt or execution authority. `/asen-agents` keeps the existing row order, width bound and task-ID-before-summary layout, but replaces control/format characters and line/paragraph separators in displayed role, owner, ID and summary text with visible `�` characters before width accounting and truncation. This display-only boundary also applies to injected agent providers; raw lifecycle records, identity, state and persistence remain unchanged. It does not add identifier rewriting, redaction or a grapheme-aware column guarantee. Structural newlines between notified rows remain layout.

Terminal notifications are scoped to the active owning session/project; recovery never replays prior execution. Todo-bound starts, continuations and retries persist ownership before dispatch and revalidate Pi identity at the locked launch boundary. `asen_agent_continue` requires explicit confirmation; `asen_agent_retry` permits one explicitly confirmed retry of a failed linked read-only plan task. The agent tools accept optional absolute `root`; launching in a different project requires affirmative Pi UI consent, and later calls require that same live permission. Session-manager changes and shutdown remove it, and continuation never reconstructs permission from saved records. Public tasks remain read-only; existing internally authorized write agents keep their separate pinned authority and attribution boundary. Session shutdown cancels owned active tasks across all projects launched by this runtime.

ODD task mirrors preserve their saved history: initial registration creates a record only when its task/candidate identity is absent. Re-registering that identity is rejected; resume the saved task or choose a fresh identity. Replay events use conditional memory writes so a newer saved record cannot be overwritten by an older plan. Neither operation restores execution permission.

The internal `readProjectMemoryBackup` API reads one explicitly selected absolute path as an ordinary non-symbolic-link file. It performs a finite read of at most 16 MiB plus one overflow byte, rejects source metadata or physical-identity drift, requires strict UTF-8 and JSON, and validates the exact envelope, canonical project export, project identity, payload byte count and domain-separated SHA-256 digest. Refusals return bounded reason codes without returning partial backup data or echoing file contents. The source and neighboring files are not modified.

Reading a valid backup does not authenticate its publisher or make its plaintext trusted. The reader does not open a memory store, import, merge, replace, stage or restore data, choose a target, grant permission, or confer runtime, session, maintenance or execution authority. Restore policy and safe store reopening remain separate lifecycle work.

The internal `stageProjectMemoryBackupRestore` API is the next isolated technical boundary. It accepts only an explicit absolute backup source, nonblank expected project, explicit absolute staging directory and fixed `new-empty-stage` mode. The staging path must be absent beneath an existing ordinary non-linked parent. It delegates validation to `readProjectMemoryBackup` before creating anything, then exclusively creates and retains one private stage directory, imports into a fresh `memory.db`, verifies the exact canonical export, closes, reopens, verifies again and closes before reporting `staged`.

This API never selects or opens the live memory store, merges into an existing database, replaces, promotes or activates data, and never treats backup metadata or session status as authority. Abort or failure after creation retains a stage only while its physical ownership remains proven; replacement makes ownership unknown and triggers no deletion. Results expose bounded status, reason and ownership codes rather than raw errors or backup plaintext. A successfully reopened stage is still only staged data, not an approved restore.

The internal `planProjectMemoryRestore` API is a pure, conservative projection over explicitly supplied descriptive facts for a hypothetical dedicated-store replacement. It performs no filesystem, SQLite, extension, SDK, host or network work. Paths, physical identity, ownership, lifecycle, bindings, collisions and WAL/SHM labels are untrusted caller assertions; even complete-looking assertions cannot establish trusted evidence, a memory-specific maintenance lease, a pre-effect backup, rollback, extension rebind or human confirmation.

Every result is therefore blocked, non-executable, unauthorized and requires revalidation. The bounded blocker list never echoes supplied paths, project identifiers, digests, receipt references or descriptions. This API is not an effectful restore, a consent request, an approval, or proof that a live target is safe. Restoring or replacing a live memory store remains unimplemented and requires separate trusted collection, rollback/rebind proof and explicit one-shot human maintenance consent.

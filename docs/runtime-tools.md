# ASEN runtime tools and registry lifecycle

These interfaces are registered by the shipped primary extension (`asen/extensions`). They are bounded implementations, not complete ecosystem parity. The current claim registry remains authoritative; local fixtures do not establish all-platform host behavior.

## User interaction

`asen_ask_choice` accepts a question, optional header, and two to four options. Each option has a label, optional description/preview and a unique value. `ask_user_choice` is the canonical compatibility alias: it uses the same strict input checks, excludes `preview`, and reports the selection index starting at one. The ASEN-named tool keeps its existing zero-based index.

`asen_ask_question` accepts one to four questions. Each has a question, header and two to four labeled options; `multiSelect` is optional. `ask_user_question` is registered as a compatibility name and currently uses this ASEN input and result shape; exact canonical result translation is still pending. A cancelled questionnaire discards all partial answers. Custom free text, where explicitly enabled by the choice contract, is validated and remains data. Neither tool issues permissions or a write grant.

The native Pi select/input primitives carry interaction. Offline Linux RPC choice/cancellation has been tested with zero model turns. Full TUI/questionnaire presentation and integration with genuine human-only mutation consumers remain open. Timed-out hosts that ignore abort stay quarantined until the old dialog settles.

## Code intelligence

Pi exposes one CodeGraph tool: `codegraph`. It accepts `operation` (`init`, `query` or `explore`), an optional integer `limit` from 1 to 20 (default 10), and a nonempty query of at most 2,000 characters for query/explore. Read-only query/explore calls run without an ASEN confirmation and never initialize or retry automatically. `init` may create `.codegraph` only after a one-run approval in Pi's interactive UI; headless execution, denial, or cancellation performs no initialization. A successful index initialization is not repeated in the same Pi process, and an existing safe index is left alone.

The `asen_code_intelligence` adapter remains available to existing internal callers during migration, but is no longer registered with Pi or shown to the agent. It accepts only `query` or `explore`, requires the query, preserves its existing bounded statuses, and cannot initialize an index. CodeGraph requires the current working directory to be the canonical Git project root. Home/temp roots and nested working directories are rejected. Existing `.codegraph` entries are checked with `lstat`; symbolic links and non-directories are rejected without reading index contents.

Both names share hardened execution. The host resolves an installed CodeGraph executable; on Windows, npm package metadata resolves a contained JavaScript entry through Node rather than executing cmd/PowerShell shims. Processes use separate arguments, a constrained environment, no shell, bounded duration and bounded output. Queries follow `--`, so they remain one literal argument. Canonical output is truncated with an explicit marker; canonical failures include operation, workspace and fallback metadata. Compatibility failures remain sanitized and do not expose subprocess error output.

Tests use injected subprocesses and disposable Git fixture projects, including spaces/Unicode paths, hostile queries and unsafe synthetic index entries. No canonical `init` is invoked against an ambient workspace. Real CLI/version compatibility, initialization against a disposable real-CLI project, and cross-platform host behavior remain open. The installed CLI is trusted local code; this is not OS confinement. Existing authority gates still determine whether a tool may execute.

## Skill registry lifecycle

Startup refresh reuses `.asen/skill-registry.md`, its existing cache and optional memory mirror. Source precedence remains project, user, then package scope. Discovery does not alter mandatory behavior-Skill selection.
Repeated activation through the same loaded module and Pi host registers only one startup hook; separate copies loaded through different module paths still require real-host validation.

Interactive hosts watch existing source roots recursively, debounce changes and serialize writes per canonical project. Changes during refresh coalesce into a follow-up refresh. Project switching/shutdown invalidates old callbacks; shutdown closes watchers, cancels scheduled refresh and waits for in-flight work. Unsupported watchers produce a diagnostic and leave manual refresh available. Missing or recreated source roots may require manual refresh or restart.

Disable automatic startup/watch with either of:

- environment variable `ASEN_NO_SKILL_REGISTRY=1` (`true`, `yes` and `on` also apply);
- Pi `--no-skills` or `-ns`.

ASEN does not register a separate CLI flag because Pi's public extension API has no complete flag inventory for collision checks.

`/asen-skill-registry refresh` remains an explicit manual command. Startup/watch failure is diagnostic; it does not cancel the user's final response. Local native Linux watch invalidation, restart generation, shutdown, disable and project isolation are tested. Real all-platform Pi startup/restart journeys remain open.

## Project memory

The primary Pi extension opens the private local SQLite store at `~/.asen/memory.db` when memory is enabled. At session start it binds a fresh memory session to the canonical current project and Pi session. Before each agent turn it adds only bounded project context: recent/pinned notes on the first turn and project-search matches for later requests, capped at 4 KiB. A project/session mismatch or unsafe store prevents memory access and never broadens retrieval to another project.

`asen_memory_save` stores curated project decisions, conventions and non-obvious discoveries. `asen_memory_search` retrieves bounded matches. The injected policy tells the agent to avoid transcripts, routine actions, credentials, personal data and temporary task checklists. On session shutdown ASEN stores a short summary of notes saved during that session; the next session can read it. A crash may skip the summary, but saved notes remain durable. Memory remains reference data and never restores write permission or resumes a task.

`/asen-memory status`, `/asen-memory search <text>` and `/asen-memory forget <id>` let the user inspect or remove local notes. Forget requires a live Pi UI confirmation and removes the affected session summary so deleted content is not reintroduced through that summary. Search and context remain project-scoped.

These deterministic lifecycle tests use a local SQLite file and simulated Pi events; they do not establish a provider-backed Pi conversation or cross-platform host evidence.

## Primary installation and child policy

The Pi package manifest selects `extensions/asen.ts` explicitly. `extensions/authority.ts` is a private, hash-pinned policy loaded explicitly by the existing child runner; ordinary installation must not apply it to the primary session. `verify:pack` installs the actual tarball with the optional peer omitted, asserts that the peer is absent, then loads the tarball through the real Pi SDK resource loader and rejects accidental child-policy activation. This offline registration check does not execute tools or models, and does not prove complete ecosystem integration.

ASEN child Pi agents receive no provider credential by default. To route controlled agents through NVIDIA NIM, configure the Pi profile at `~/.asen/profiles.json` with an active profile that defines the required role routes, for example `{"schema":"asen.runtime-profiles/v1","active":"nvidia","profiles":[{"name":"nvidia","routes":{"worker":{"model":"nvidia/nemotron-3.5-lightning-30b-a3b","thinking":"low"},"reviewer":{"model":"nvidia/nemotron-3.5-lightning-30b-a3b"},"verifier":{"model":"nvidia/nemotron-3.5-lightning-30b-a3b"}}}]}`. Set `NVIDIA_API_KEY` in the process environment and `ASEN_AGENT_PROVIDER_CREDENTIAL=NVIDIA_API_KEY`; ASEN then passes only that selected credential to child Pi processes. The selector accepts only the provider credential names in the Pi runner allowlist, never accepts credential values, and is not itself forwarded to children. Do not store API keys in the profile file. This config routes delegated agents; it does not change the model selected for the primary Pi session. If no selector is configured, child processes receive no NVIDIA credential and authenticated NVIDIA calls cannot run.

## Public Pi command boundary

The production factory accepts the declared Pi range `>=0.85.1 <2.0.0` and validates its public registration APIs before adding a bootstrap session handler. Pi does not provide mode or initialized command/tool inventories to the factory, so ASEN follows the normal delayed-activation policy: at the first `session_start`, after Pi initializes those public inventories, ASEN validates the execution mode and complete command/tool snapshot before its first command or tool mutation. Missing, malformed or initially colliding inventories fail closed and may retry on a later session; a host error after partial registration leaves those handlers inert and requires a Pi reload. This preserves ASEN's initial collision preflight, not an arbitrary late-registration veto.

After that initial snapshot, foreign extensions that register duplicate names are governed by Pi's native precedence and disambiguation behavior. Pi exposes no public registration interception or complete flag inventory, so ASEN neither guarantees a late sibling veto nor registers a private CLI flag. Command, tool and event handlers still validate the public execution context mode (`tui`, `rpc`, `json` or `print`) before running. Prior packed-artifact checks on Linux exercised real Pi `0.85.1` and `1.1.0` CLIs with seven visible RPC commands, four canonical tools, and zero model calls; the current candidate's expanded command list is verified separately by `verify:pack`. Windows/macOS, clean exit across all four modes, and representative coverage of the full supported version range still need real-host validation.

The data commands publish through `ctx.ui.notify`; their production handlers fulfill Pi's `Promise<void>` contract. Internal `createAsenExtension` handlers retain their returned data for composition/tests. `/asen-route` remains an advanced read-only diagnostic for exact ODD facts; ordinary users can describe the task in chat. The Pi coordinator is instructed to inspect the active project read-only, derive ODD facts internally and call `asen_plan_request` for tracked or multi-step work. That tool creates the task identity, binds the repository to the active Pi project, and passes the derived facts through the same ODD decision, orchestrator, skill selection and executable DAG. With the Todo runtime enabled, the plan is persisted atomically as session/project-owned tasks and dependencies; planning does not retrieve information, request review, issue execution authorization, or dispatch agents. The lower-level `/asen-plan` command remains an internal materializer for callers that already have validated ODD facts; plain text there returns conservative missing-fact triage. `asen_plan_dispatch_next` continues one dependency-ready primary task in the active session or automatically dispatches one read-only role (`explorer`, `reviewer`, or `verifier`) after checking current skill selection and session/project identity. Material clarifications pause for the user. A writer still requires a fresh candidate and explicit authorization limited to its exact file scope; linked results remain blocked until independently accepted.

When a plan is active, `before_agent_start` adds a short role/status summary to the prompt for the exact current Pi session and project. It omits task IDs and task descriptions, is capped at 2 KiB, and is reference-only: it neither resumes blocked work nor grants permission. If the Todo store is unavailable or identity changes during retrieval, the turn continues without the summary.

`/asen-changes` is filtered to the current session, canonical project and worktree. It flags a potential conflict when successive successful change records for one relative path name different actors. Windows and macOS comparisons fold path case to catch common case-insensitive collisions; this can conservatively report distinct names on a case-sensitive macOS volume. The append-only store has no content snapshots, so this is a review signal only: it does not prove a lost update, select a winner, clear a conflict, or authorize a write. The command does not inspect another session's changes. Authorized resolution and broader workspace actions are not implemented.

`asen_todo_update` requires active Pi UI confirmation before resuming a blocked Todo. A planned task needs a verification summary and user confirmation before completion; if a Pi agent is linked, direct completion is rejected. Use `asen_todo_accept_result` to select the exact persisted linked agent result. It requires matching session, project and planned role, a successful terminal record, a complete result that fits the bounded review view, independent user evidence, and explicit Pi UI acceptance. Acceptance is written as `running` then `done`, so interruption between those events recovers to review. Agent completion alone never closes a Todo.

After a planned Todo is independently accepted as `done`, ASEN automatically checks for and starts the next dependency-ready task. Read-only steps continue automatically; a writer still receives the existing exact-scope Pi approval. If advancing fails, the accepted result remains saved and the user can simply ask ASEN to continue; internal task IDs and slash commands are not required.

Agent task delivery and project access: `asen_agent_status` accepts an optional `id` to return that owned task's durable state and history without its prompt or execution authority. Terminal notifications are scoped to the active owning session/project; recovery never replays prior execution. Todo-bound starts, continuations and retries persist ownership before dispatch and revalidate Pi identity at the locked launch boundary. `asen_agent_continue` requires explicit confirmation; `asen_agent_retry` permits one explicitly confirmed retry of a failed linked read-only plan task. The agent tools accept optional absolute `root`; launching in a different project requires affirmative Pi UI consent, and later calls require that same live permission. Session-manager changes and shutdown remove it, and continuation never reconstructs permission from saved records. Public tasks remain read-only; existing internally authorized write agents keep their separate pinned authority and attribution boundary. Session shutdown cancels owned active tasks across all projects launched by this runtime.

ODD task mirrors preserve their saved history: initial registration creates a record only when its task/candidate identity is absent. Re-registering that identity is rejected; resume the saved task or choose a fresh identity. Replay events use conditional memory writes so a newer saved record cannot be overwritten by an older plan. Neither operation restores execution permission.

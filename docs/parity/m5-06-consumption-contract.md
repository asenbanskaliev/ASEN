## What ships here (pure, CI-independent)

- `observationsFromC01Report({report,readiness,artifactPath})` in `scripts/shell-asen-parity.mjs`:
  converts one graded C01 beam report (`asen-r4-c01-two-real-pi-inferences/v1`) into the
  `asen-shell-asen-observations/v1` pair that `compareShellAsenClaims` already consumes.
  Identity gates run first: candidate/reference SHA equality against the readiness, frozen
  reference commit, plausible `runId`/`runAttempt`, exactly two distinct sources, a canonical
  non-symlink artifact path, and artifact bytes that deep-equal the report. A report that already
  carries promotion state (`certifiedFullCases≠0`, `globalFull`, `independentReviewPerformed`) is
  refused. `execution:"real"` is emitted only from the bounded agent-start proof.
- `attestC01Comparison({comparison,consentReceipt,reviewRecord,runContext})`: with no inputs it
  returns the comparison byte-identical (verdicts stay `*_CLAIM_UNATTESTED`); a partial pair
  (consent without review, or review without consent) fails closed; with both genuine inputs only
  the per-case claim status upgrades to `*_CLAIM_ATTESTED` for exactly one run identity. The
  certified counters stay zero and `globalFull` stays false in every path — registry stage
  advancement remains owned by CI assembly and independent acceptance.
- `validateParityConsentReceipt` / `validateParityReviewRecord`: the UFC-M5-02 execution schema.
  Consent: owner identity, exact candidate SHA, decision fixed to
  `consumption-and-attestation-wiring`, run-bound so replay into another run throws.
  Review: reviewer identity must not carry the owner prefix, approved verdict only, non-empty
  findings, same SHA/run binding. The reviewers and grants live outside the repository; nothing
  here fabricates either input.

## Receipt provenance verification (added for the owner's contract review, 2026-11-08)

The owner requires that consent/review receipts are not merely well-shaped but of **verified real
provenance** before any promotion wiring. The current validators check structure and identity
binding only — they cannot distinguish a genuine owner signature from a locally crafted file with
the same fields. The consumption contract therefore stays incomplete until the provenance mechanism
below (or an owner-better alternative) is chosen and implemented.

### Threat model

Inside a CI runner that checks out attacker-influenceable code, ANY file committed to the
repository — or written by any step — is attacker-controllable. A signed-blob-in-repo design is
forgeable by whoever can push to the branch. Therefore:

1. **Repository contents are NOT a provenance source.** No receipt file may be tracked, committed,
   or generated by a build step.
2. **Provenance must come from an external trust root** whose secret never touches the runner:
   - Option P1 (recommended): GitHub **deploy keys-free signed timestamp** — owner signs the
     receipt JSON (`sha256` digest over canonical bytes) with an SSH key whose PUBLIC half is
     pinned in a tracked registry file (`registry/parity/attestation-identities-v1.json`, reviewed
     by PR like any contract change); the signature arrives as a separate artifact via
     `workflow_dispatch` input or the private-environment file channel, never as a committed file.
     The adapter verifies `sig` against the pinned public key over the exact receipt bytes.
   - Option P2: reuse the **existing GitHub environment protection rule** — the runner only marks
     `consumed` if the job ran in a reviewed environment (`environment: asen-parity-attestation`)
     whose required-reviewer gate is the consent event itself; the "receipt" is then the deployment
     review record bound by `runId`/`runAttempt`. Zero new secrets; weaker audit trail.
3. **Independence**: the review record must be signed by a key registered with kind `reviewer`
   (P1) or posted by a GitHub identity distinct from the owner and from every prior consumer of the
   same run (P2 adds an API check `review.user != consent.user`). `validateParityReviewRecord`
   already refuses `owner:` prefixes; the provenance step adds cryptographic or platform identity.
4. **Freshness**: `performedAt`/`grantedAt` must fall between `run_started_at` and the consumption
   step's own timestamp (±0 skew tolerance), so a receipt cannot pre-date the run it attests.
5. **Non-replay**: `runId`+`runAttempt`+`candidateSha` triple is recorded in a consumption ledger
   artifact and a given triple may be attested exactly once; a second workflow attempt reusing an
   old signature fails the timestamp-window check by construction.

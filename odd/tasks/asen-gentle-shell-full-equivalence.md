## Accepted engineering criteria

The owner accepted the preceding seven-rule proposal with S4. Apply these criteria in F5-F7; they do not expand implementation or execution authority.

1. **Outcome parity before improvements:** compare public results and interactions, not internal code identity. Record intentional branding/accessibility differences and reference limitations separately; do not silently certify them as exact parity.
2. **One production owner per responsibility:** each gap task identifies the existing command, store, controller, registry or renderer it reuses. A new component needs evidence that extending the existing seam is insufficient. Do not create parallel mechanisms just to resemble the reference.
3. **End-to-end acceptance:** specify complete journeys, including profile creation/model choice/fallback/task execution/cancellation/session recovery where applicable. Isolated tests complement, not replace, public journey evidence. Historical stopped proofs remain stopped.
4. **Actual visual acceptance:** compare genuine application captures at the same dimensions and states: empty, busy, error, long lists and narrow windows. Cover keyboard, mouse, focus, scroll and readability. Static screenshots and mockups are not fresh runtime parity.
5. **Measure before optimization:** establish evidence for startup, menu responsiveness, memory and cancellation before proposing optimization. No new cache, process, subsystem or abstraction without an observed problem and a proportionate benefit.
6. **Useful improvements only:** prioritize clearer states/errors, fewer steps in frequent actions, reliable cancellation/recovery, accessibility/lower visual noise, and truthful separation of unknown from verified status. These are candidate priorities, not unmeasured superiority claims.
7. **Simplify on delivery:** retain a single production path per adopted responsibility. Remove only proven duplication through compatible, ownership-safe changes; do not stack redundant adapters or blanket-delete existing behavior.

Every improvement must answer: What observed problem does it solve? What existing mechanism does it reuse? How is success checked? Does its user benefit justify maintenance? If these are unanswered, exclude or defer it. Plan parity and optional improvement tasks separately; do not inflate the parity critical path with speculative features.

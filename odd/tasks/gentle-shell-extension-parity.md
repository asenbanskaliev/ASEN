## Target architecture and non-negotiable boundaries

### Architecture slices

1. **Host capability adapter:** detect Pi API/version capabilities, session mode (TUI, print/headless, interactive RPC), primary versus managed child, canonical repository identity, and registration-name availability before feature registration.
2. **Pure domain cores:** keep Todo, prompt-history selection, usage/stat projection, shell presentation, review decoding, and public-agent lifecycle reducers independent of Pi UI.
3. **Private persistence:** retain ASEN's atomic `0600` writes, symlink rejection, lock/CAS behavior, corruption fail-closed handling, and explicit reset. Add migrations around those stores; do not replace them with weaker upstream persistence merely for structural similarity.
4. **Authority adapters:** keep review authority provider-owned, candidate views immutable, writer admission bounded, child authority separate, and user interaction authority-free.
5. **Host presentation:** register tools/commands before optional TUI. TUI adapters consume pure state and dispose every overlay/timer/listener; headless and RPC paths return structured results and never fabricate UI consent.
6. **External integrations:** provider, telemetry, HERDR, third-party `pi-pretty`, transcript import, and network catalog refresh remain separately gated product capabilities.

### Required decisions

- **Review:** execute only provider-issued transitions decoded by the versioned protocol. Never reconstruct START, consent, capture, collect, recovery, stop, or acknowledgement arguments locally. The immutable candidate review boundary must be established before capture or reviewer dispatch. Approved authority burns only after exact provider acknowledgement evidence.
- **Subagents:** expose a public, session-owned lifecycle (`run/status/result/list/reply/cancel/send/continue`) only after protocol/store and bounded hostile-output handling exist. Preserve the current default of no child shell and read-only isolation. Writer children receive exact admitted surfaces through the existing separate authority extension.
- **Shell admission:** make an explicit shell/background-tool admission decision first. If admission is denied, preserve tool exclusion. If admitted, the destructive-command guard and background-job constraints are mandatory prerequisites, not follow-up hardening; the recognizer is defense in depth, not confinement.
- **History:** preserve ASEN's opt-in, redaction-before-write, private locked store. Transcript scanning/global import requires separate informed consent, an explicit home-boundary decision, and idempotent migration; it must not silently follow extension parity.
- **Telemetry/provider/third-party UI:** default to off. Require privacy/security/license review, explicit consent, preview where applicable, environment vetoes, secret non-disclosure, cancellation, and no-network tests before activation.
- **Name collisions:** before every canonical registration (`codegraph`, `ask_user_choice`, `ask_user_question`, `todo`, subagent tools, provider names, commands, shortcuts), detect host/package collisions and fail closed or expose an explicit compatibility decision. Never silently replace foreign tools.
- **Pi API floor:** ASEN currently declares peer compatibility from `>=0.85.1`; every planned use of provider registration, live orchestrator/model switching, tool renderers, fullscreen UI, blocked events, editor/prompt ownership, RPC dialogs, or built-in tool factories must be capability-tested against that floor. Raise the floor only as an explicit compatibility change with host-matrix evidence.

### Per-capability observable obligations

Every future implementation must prove the applicable obligations, not merely register a matching name:

- **Security:** canonical root/common-dir identity, symlink/path traversal rejection, owner-private persistence, terminal/control sanitization, secret non-disclosure, bounded input/output/frame counts, and registration-collision handling.
- **Errors:** stable typed/structured failure in headless/RPC modes; no raw credential/path leakage; corrupt authority/persistence fails closed; UI failures do not mutate state.
- **Cancellation:** propagate `AbortSignal`; distinguish pre-launch no mutation from unknown post-launch outcome; dispose dialogs, timers, process trees and overlays; reconcile provider mutations by STATUS.
- **Persistence:** state ownership, schema/version, atomicity, locks/CAS, session/clone identity, restart hydration, corruption/reset, migration rollback and cleanup are explicit per store.
- **UI:** TUI is optional presentation over pure state; width/control text/mouse/keyboard behavior is bounded; headless and RPC never wait for unavailable UI; blocked events always balance.
- **RPC:** exact schemas and result envelopes, ownership/session checks, bounded query rounds, stale-result behavior, cancellation, and no implicit human consent.

## Rollback design

- Ship each EP behind a capability/registration boundary; disabling a new adapter must restore existing ASEN behavior without store conversion.
- Additive stores use versioned schemas and write only after successful validation; migrations retain or can reconstruct the prior canonical file until acceptance.
- Review mutations cannot be rolled back locally. Rollback means disable further transition execution, retain provider lineage/status evidence, and require provider-directed recovery; never fabricate reversal.
- Candidate-view replacement is transactional: failed replacement preserves the prior valid view and registry binding.
- Profile/model changes use compensation to restore the previous materialized/live state on partial failure.
- Public-agent cancellation must confirm process cleanup or quarantine capacity; it must not report rollback of already observed child mutations.
- UI adapters own and dispose only their registrations/overlays/timers; third-party UI/provider/telemetry/HERDR integrations remain separately removable.
- History/import rollback restores the pre-migration private store and never deletes source transcripts. Disabling capture preserves existing history.
- No EP may require reverting EXT-01's approved canonical/compatibility CodeGraph tools; advisory fixes remain small isolated follow-ups.
